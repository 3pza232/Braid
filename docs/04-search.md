# 搜索

侧栏搜索框有**两种模式**，靠搜索框右边那颗按钮切换（`标题` / `正文`）。

| 模式 | 范围 | 实现 |
|---|---|---|
| 标题 | 会话列表，**本地内存** | `domain/rules/fuzzyMatch.ts`（子串 + 顺序子序列） |
| 正文 | **跨会话**，但每个会话只搜它**当前可见的那一条路径** | 见下 |

## 正文搜索的语义（这几条都是刻意定的）

1. **只搜看得见的内容**。旧分支（编辑、"重新生成"留下的）仍在库里，搜出来也跳不到 ——
   用户按「下一处」只会对着空白屏幕点；
2. **不搜工具结果**。那是机器输出（目录清单、文件正文、接口返回），体量最大、噪声最多，
   而且它渲染在悬浮面板里且有长度上限，命中了也看不见。找文件内容请直接找文件；
3. **搜思考过程**。模型琢磨过什么常常比正文更有辨识度。命中若**只在**思考过程里，
   跳过去时会自动展开那个折叠块；
4. **命中粒度是"词"**，不是"消息"。同一条消息里出现 8 次同一个词 = 8 处命中，
   `上一处 / 下一处` 逐处走；
5. **顺序**：会话按最近使用（与侧栏一致）→ 会话内**从上到下**。

## 三层结构

```
① 粗筛  MessageStore.findCandidates(query, 300)
        SQLite 内 LIKE 扫 segments_json，**只回传命中行**（不把整库读进内存）
   ↓
② 轻查  MessageStore.listLinks(命中会话)
        只取 id / conversation_id / parent_id / active_child_id —— **不读正文**
   ↓
③ 精判  messageSearch.searchVisibleAcrossConversations()
        用 activePathIdsOf 算出各会话当前可见的路径，滤掉旧分支，再逐处定位
```

**② 是这套做法能成立的关键**：判断"某个节点在不在当前分支上"只需要指针，
把每个命中会话的正文全读回来（几百 KB 起）只为走一遍指针，是这里最容易被写出的浪费。
**③ 是唯一保证"每条结果都看得见"的地方** —— 粗筛必然把旧分支捞出来，只有路径判定能挡住它。

纯函数在 `application/chat/messageSearch.ts`，有单测（`tests/application/messageSearch.test.ts`）：

- `searchActivePath(path, query)` —— 单条路径上的逐处定位；
- `searchVisibleAcrossConversations({candidates, pathByConversation}, query)` —— 跨会话组装。

## 边界与常量

| 常量 | 值 | 含义 |
|---|---|---|
| `CANDIDATE_LIMIT` | 300 | 粗筛最多取回多少条候选（内存上限） |
| `MAX_HITS` | 200 | 结果上限（超过就没人看了，"下一处"也变成折磨） |

- 一条极长的会话若有 300+ 处命中，会把其他会话的命中挤出候选池 —— 这是**已知取舍**，
  要调就改这一处；
- 粗筛那次 `LIKE` 是唯一与库大小成正比的操作（把整表字节读一遍），本地几 MB 量级感觉不到；
  涨到几十 MB 时该换 **FTS5 索引表**（换的只是①，②③不动），但届时必须一并解决中文分词
  （FTS5 默认不吃中文，要用 trigram 或预分字）。

## 界面侧

| 位置 | 行为 |
|---|---|
| 侧栏提示 | `3 个会话 · 12 处命中` ↔ `第 4/12 处 ·《会话标题》`（跨会话时必须告诉用户会跳到哪去） |
| `‹ ›` | 前后跳一处；命中在别的会话里会**自动切会话**（切过去一定看得见） |
| 会话列表 | 正文模式下收窄到"有命中的会话"；点一条会话会跳到它**第一处**命中 |
| 高亮 | 全部命中淡底；**当前那一处**实底 + 反色，且强调的只是**那一个词** |

### 高亮怎么实现的（以及为什么不能插 `<mark>`）

`ui/utils/searchHighlight.ts` 用的是 **CSS Custom Highlight API**（`::highlight(...)`），
名字在运行时注册，样式在 `ui/styles/searchHighlight.css`（**全局样式**，CSS Module 的哈希类名
在这里不适用）。

为什么不用"往 DOM 里插 `<mark>`"：React 记着自己渲染了哪些节点，插进去的节点它不知道，
下一次重渲染（流式输出每 120ms 一次）它去移除子节点时就会抛
`NotFoundError: The node to be removed is not a child of this node` ——
那种错误只在特定时序下出现，极难复现。

代价是高亮挂在**文本节点**上，节点一换就作废。所以 `MessageList` 装了
**MutationObserver**：DOM 一变就用同一份参数重画（用 rAF 合并同一帧内的多次变动）。
流式替换正文、思考过程展开、切换变体…… 都靠它自愈。

### 跟随滚动：先立框，再立词

`revealRange(range, scroller)` 分两级对齐，且顺序不能反：

```
内层：把**词**对齐到思考面板中间    （这层回答"在框里看哪一句"）
外层：把**面板这个框**对齐到可视区中间（这层回答"看哪个框"）
```

若外层也对齐"词"，320px 高的面板会有一半被推出屏幕 —— 就是"结果贴在框外面/上面"。
每层都取**当次实测**坐标：内层滚动会改变外层坐标，用旧值算外层必然偏。

两条相关的细节：

- 命中在没有渲染出来的折叠块里时（思考过程），滚动要**等展开之后**才做得了 ——
  所以用了一个"**滚成功才清掉**"的标记，第一次绘制拿不到区间就留给 DOM 变化后的重绘补；
- 思考面板默认"流式输出时跟到底部"，这会顶走刚对齐的位置。搜索正聚焦在某条消息上时，
  该面板**暂停跟随**（`MessageItem` 的 `autoExpandReasoning`）。
