# 工作区与文件工具

模型可以读写你选择的**一个目录**。这是整个应用里唯一能碰到"目录之外"的能力，
所以权限被拆成了三件事分别表达。

## 三个工具

定义在 `application/tools/workspaceToolRegistry.ts` 的 `DEFINITIONS`：

| 工具 | 参数 | 会改数据 | 上限 |
|---|---|---|---|
| `list_dir` | `path?`（省略=根目录） | 否 | 200 条 |
| `read_file` | `path` | 否 | 20000 字符（超出截断并**注明**） |
| `write_file` | `path`、`content` | **是** | —— |

`write_file` 会**自动创建缺失的中间目录**，所以"新建目录 + 写文件"一次调用就够。

**失败不是异常**：`run(call)` 从不抛错，它返回"给模型看的一句话 + `isError`"。
工具失败是对话的一部分 —— 模型需要知道"写失败了，因为没权限"，才能换个做法。
参数 JSON 残缺时会**拦住并说明原因**（最常见是单次输出上限把参数截断了），
而不是含糊地报"缺少参数"。

## 权限模型

**一个动作就够了**：选中工作区目录 = 允许 AI 在该目录里读写。

唯一的入口是**会话设置与顶栏**（全局设置里**没有**工作区这一页 —— 工作区是每个会话
各自选的目录，不是全局默认值，放在全局设置里只会让人问"那到底是哪个目录"）。
会话设置里那一行的按钮是「移除引用」：只让 Braid 不再引用这个目录，目录里的文件一个字都不动。

| 动作 | 条件 |
|---|---|
| **读** | 选中了目录 + 浏览器对该句柄 `granted` |
| **写** | 上面两条 **且** `writeState === 'granted'`（浏览器给了写入授权） |

**【这里曾经有三层开关，已整个删掉】** 全局默认（`settings.workspace.allowEdit`）+
会话覆盖（`conversation.allowWorkspaceEdit`，三态）+ 浏览器授权，三者缺一不可 ——
迁移 v10 把那一列也删了。用户点开目录选择器、选中一个目录，本身就是同意；
三层开关只会让他看到"我明明选了目录、也开了开关，它还是说没权限"，
而界面上看不出是哪一层的问题。

写入授权必须来自**用户手势**，所以：

- `selectDirectory` **一律**申请 `readwrite`（这是唯一同时具备"用户手势"和"授权弹窗"的时机）；
- `WorkspaceApi.authorizeWrite()` 必须在点击处理函数里**同步地、先于任何 `await`** 调用 ——
  浏览器只在手势的同一个任务里认这个请求。它现在只用于"授权偶尔失效"时补一次。

`writeFile` 是**唯一的写门禁**，现在只有两道检查：目录还在吗、浏览器放行了吗。
缺哪一样就说清哪一样（`FS_EDIT_DENIED` + 一条用户可见的警报），而不是含糊地"没权限"。

## 路径沙箱

`domain/rules/workspacePath.ts`：

- 只接受**相对路径**（如 `小说/第一章.txt`），不接受绝对路径、盘符、`..`；
- 归一化后拒绝：空、绝对、盘符、越界、含 NUL、层级过深（> 48）；
- `write_file` 的路径也会走同一套校验。

**沙箱的安全性不靠字符串前缀比较**，而是"交给句柄 API 解析 + 结构性不越界"：
即便路径写得再刁钻，最终的句柄解析也不会跑出选中目录。

## 句柄怎么存

浏览器的目录句柄不能序列化进 SQLite，所以：

```
IndexedDB（adapters/host/handleStore.ts）  ← 令牌 → FileSystemDirectoryHandle
SQLite（conversation.workspace_root）      ← 只存那个**令牌**
```

好处：数据库可以随便复制/备份，不会顺带泄露目录访问权。代价：换了浏览器配置之后
需要重新选择目录（浏览器也可能要求重新确认授权）—— 界面上的「重新授权」按钮就是干这个的。

### 授权能活多久 —— 以及桌面版为什么能跨重启

浏览器对 File System Access 的授权**跟着顶层文档走**：最后一个顶层文档关闭或导航离开后
不久，那个 origin 的授权就被重置。它是三个"看起来像坏了"的症状的共同根因：顶栏一直挂着
「需授权」、每次重开都要重新授权、以及"设置里刚授权完，会话里还得再点一次"。

- **桌面版把它修好了**：`electron/main.cjs` 里实现了 `setPermissionCheckHandler` 与
  `setPermissionRequestHandler`（Chromium 的 FSA 授权正是交给宿主决定的），放行
  `fileSystem`。两个坑：权限名是**驼峰** `fileSystem`（写错大小写永远匹配不上），
  而且它的 `isMainFrame` **永远是 false**（Chromium 的限制），判断不能依赖它。
  **放行的代价要讲明白**：浏览器那一层不再是门禁 —— "能不能写"完全由 Braid 自己的
  编辑开关说了算（开关没开时 `writeFile` 连底层写接口都不会调用）。桌面版这样做是合适的：
  用户在目录选择器里选中一个目录，本身就是一次明确的授权；
- **浏览器版没有这个口子**（那是宿主行为），那边仍可能要求重新确认；
- **取消授权**：FSA **没有**"撤销已授予权限"的 API，所以能做的是让 Braid 不再引用它 ——
  删掉保存的句柄、清空会话的工作区（界面上叫「移除目录并取消授权」）。
  目录里的文件一个字都不会动，之后想用再选一次；
- **写入授权成功后要连同读取状态一起重查**（`authorizeWrite` 走 `load()`）：浏览器给
  `readwrite` 时读权限是一并给的，只更新 `writeState` 会让顶栏那颗「需授权」亮着不走，
  用户刚点过授权还得再去会话设置里点一次「重新授权」（真实反馈）。
  `tests/application/workspaceService.test.ts` 里有一例专门钉它。

## 系统提示词里的工作区说明

`workspaceToolRegistry.promptSection()` 会生成一段能力说明追加到系统提示词。它有两个要求：

1. **稳定内容在前、易变内容在后**（工具说明、路径规则在前；目录名、当前权限状态在后）——
   提示词缓存是"最长公共前缀"匹配，而这段位于消息数组最前面，
   中间插一个会变的东西会让它后面的全部内容每轮失效；
2. 讲清"为什么现在不能写"，要**讲到能照着做**的程度（去开开关 vs 去点授权是两件不同的事，
   混成一句"没权限"会让模型反复重试、让用户到处找）；
3. **"说有工具"必须等于"发了工具"**：发不发 `tools` 声明由 `specs()` 按 `canRead` 决定
   （选了目录 **且** 浏览器已授权读），所以 `promptSection()` 也必须用同一个判据。
   早先它只看"选没选目录"，于是最坏的一种组合会出现：系统提示词里列着三个可用工具，
   而这次请求**根本没带 `tools` 字段** —— 模型据此向用户宣称"我可以读你的文件"，
   一调用就什么都没有。重开浏览器后目录授权常要重新确认，这条路径真的会走到；
4. **权限措辞不能变成"行为邀请"**：这里曾经写"编辑权限：已开启且已授权，可以直接写文件，
   无需再次询问"。用户实测的后果是 —— 让它写长内容时，它把正文写进了文件，
   理由是"`write_file` 在场是很强的行为邀请，还标注了已授权、无需再询问"。
   所以现在改成"能写不等于该写（仍需用户明确要求）"，并单独写了一条**使用原则**：
   "只在用户明确要求读写文件时使用这些工具；用户要长文时直接写在回复里"。
   `write_file` 的描述里也带了同样一句（模型可能只读工具声明）。
   这条不变量由 `tests/application/toolRegistry.test.ts` 钉住（含"不得出现邀请语"的反向断言）。
