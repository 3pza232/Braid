# UI 层

界面代码占全仓一半以上（33 个组件 + 14 个 ts + 23 个 CSS），之前没有文档。
这一篇讲**东西放在哪、按什么规矩写**，不讲像素细节（那看组件旁的 `*.module.css`）。

## 目录分工

| 目录 | 装什么 | 例子 |
|---|---|---|
| `ui/components/` | 常驻布局与消息区里的东西 | `Sidebar`（会话 + 角色 + 搜索）、`TopBar`、`MessageList`、`MessageItem`、`Composer`、`ContextMenu`、`Notices` |
| `ui/panels/` | **覆盖层**面板（按需加载） | `SettingsPanel`（外壳）+ `panels/settings/*`（10 个分区）、`RolesPanel`、`ConversationSettingsPanel`、`MetaFieldList`、`ModelProfiles`、`ThemeColors` |
| `ui/primitives/` | 无业务语义的基础件 | `Tooltip` / `HelpTip`、`Dropdown`、`DragHandle`、`Controls`（按钮、开关、数字框、分段…） |
| `ui/stores/` | zustand store，界面状态的唯一来源 | `chatStore`、`settingsStore`、`rolesStore`、`uiStore`、`balanceStore`、`workspaceStore`、`storageStore` |
| `ui/hooks/` | 可复用的交互逻辑 | `useDragReorder`（拖动排序）、`useAnchoredLayer`（锚定浮层：portal + 定位 + 翻转 + 关闭，`Dropdown` 与 `ContextMenu` 共用）、`useModalFocus`（模态面板的焦点陷阱与焦点归还） |
| `ui/theme/`、`ui/styles/` | 主题编译与全局样式 | `ThemeProvider`、`global.css`、`searchHighlight.css` |

## 数据流

```
bootstrap/createContainer（组合根：装配端口与适配器）
      ↓ App 里 bind 一次
ui/stores/*（zustand）
      ↓ 组件只做两件事：读 store、调 action
ui/components、ui/panels
```

两条硬规矩：

1. **会改动会话/消息状态的调用一律走 store**（如 `chatStore.send`），不能直接调服务 ——
   否则同一份状态会出现两个来源。至于**一次性能力**（文件对话框、备份导出、导出会话），
   组件可以直接用 `container` 上的端口：它们不改状态，经 store 中转只是多一层转发
   （`TopBar` 的备份导出与 `Sidebar` 的会话导出都是这么做的）；
2. **面板按需加载**：`SettingsPanel` / `RolesPanel` / `ConversationSettingsPanel` 在 `App.tsx` 里
   `lazy()`，合计约 90KB 源码，而日常聊天一个都不会打开。`Suspense` 的 fallback 是 `null`
   而非转圈 —— 面板是覆盖层，闪一下比先冒出一个会跳动的加载圈更不打扰。

## 层叠纪律（踩过坑，现在有门禁）

刻度定义在 `adapters/themes/primitives.ts` 的 `zIndex`，组件只用 `--z-*` 引用：

```
base 0 → dropdown 100 → sticky 200 → overlay 300 → modal 400 → toast 500 → tooltip 600
```

`check:styles` 拒绝裸数字与不存在的 token 名（`var(--z-popover)` 这种写错的名字会静默失效，
一眼看去"用了 token"，其实什么都没生效）。

两条真实事故与由此定下的规矩：

| 事故 | 原因 | 现在的做法 |
|---|---|---|
| 消息区右下角的"回到最新"浮在设置面板之上，点它却"没反应" | `.scroller` 不是层叠上下文，那个 `z-index` 直接参与**根层叠**排序；点它滚的是被面板挡住的消息区 | `.scroller { position: relative; isolation: isolate }` —— 消息区自成一层，里面的东西再怎么写 z-index 也压不过覆盖层 |
| 顶栏上下文菜单"没浮在上层、被挡住了" | 它 `position: absolute` 挂在顶栏里，而主区是 `overflow: hidden`（三个区域各管各的滚动）→ 一出边界就被裁掉 | **覆盖层一律 portal 到 `body` + `position: fixed`，坐标由触发元素量出来**（`Dropdown`、`ContextMenu` 都是这套） |

## 拖动排序

- 算法与事件都在 `ui/hooks/useDragReorder.ts`：**按 id 而不是按下标**（列表会被搜索过滤、
  会折叠，下标随时变），纯函数 `moveIdTo` / `moveIdBy` / `dropTargetFor` 单独可测；
- **接线有两处，缺一不可**：`handleProps` 挂手柄（拖动起点 + 键盘路径），
  `listProps` 挂**列表容器**（投放判定），每一行还要写 `data-drag-id={id}` 标出边界。
  投放判定放在容器上而不是每一行上，是因为指针**可能不在任何一行上**：
  列表底部的空白区（`.list` 是 `flex: 1`，内容不足时全空）没有元素挂 dragover/drop，
  "往下拖、在最后一行下面松手"这一下就会被整个忽略 —— 而那是最常见的动作。
  现在判定按 `clientY` 与各行矩形算（`dropTargetFor`：在行里就用那一行，
  在行外取纵向最近的一行），于是底部空白归到最后一项、顶部归到第一项，
  悬停时最后一行还会亮起插入线，用户松手前就能看出落点；
- 手柄统一用 `primitives/DragHandle`（三横线图标，平时半透明、悬停/聚焦变实）。
  四个列表共用同一个它 —— 早先消息信息栏与侧栏/角色面板各有一套（图标不同、显隐规则也不同），
  同一操作两副面孔，用户会当成两件事；
- 手柄有两种落位，用 `placement` 区分：
  - `inline`：行内的 flex 兄弟（消息信息栏 —— 行本身就是"标签 + 开关"）；
  - `gutter`：**绝对定位在行的左内边距里**（三个列表）。这一种是关键：手柄不占行宽，
    行盒子（含悬停底色、边框）才能与上方搜索框**同宽**。手柄若是 flex 兄弟，
    每一行都会比搜索框窄 16px、左边界也对不齐 —— 看起来就是"歪的"；
- 因此列表的横向内边距必须与搜索框的外边距一致（侧栏两侧都是 `--space-2`；
  角色面板靠 `.listPane` 的 `--space-3`，搜索框与行共用它）；行的左内边距还要
  额外留出 16px 给槽位（`calc(var(--space-2) + 16px)` 之类）；
- 键盘也要能用：手柄可聚焦，`Alt + ↑/↓` 移动（拖拽对只用键盘的人不可用，而这是功能不是装饰）；
- 三种视觉状态靠 data 属性：`data-dragging`（被拖走的那行淡出）、`data-over`（落点画插入线）、
  行容器上的手柄槽位。**运行时状态（正在拖谁、悬停到谁）留在组件内**，不写进设置。

## 提示（Tooltip）

**一个可悬停的元素只能有一个浮层**，而且必须是应用自己的那一个（`primitives/Tooltip`：
portal 到 body + `position: fixed` + 自动翻转，样式跟主题）。

- 挂上去有两种方式，按子元素的种类自动选：
  - 子元素是**原生标签**（`<button>`、`<span>`…）→ 把事件**直接克隆到它身上，不插任何节点**。
    这一点很关键：列举行是 `flex: 1` 的按钮，中间插一层包裹就会把行的伸缩算坏
    （拖动手柄那次吃过这个亏），所以侧栏的会话标题 / 角色名一度只能用原生 `title`，观感与别处不一致；
  - 子元素是**自定义组件** → 退回包一层。那种组件不一定会把不认识的 props 转发到 DOM，
    硬克隆会让提示**静默失效**（比不统一更糟）；
- 浏览器原生 `title` 是**另一套东西**：慢半拍、不跟主题、位置由系统决定。现在只剩一处：
  拖动手柄的说明（"按住拖动调整顺序"，见 `DragHandle`）—— 它是绝对定位在行左内边距里的小块，
  包一层有把行内多出一个 flex 项的风险，而它是**操作说明**不是标签，保持原生可以接受；
- **侧栏的会话行与角色行故意不挂提示**（用户明确要求）：鼠标扫过列表时不断冒出来的浮层
  比"看不到被截断的完整标题"更烦人。所以那两行既没有原生 `title` 也没有 `<Tooltip>` ——
  这是刻意的，别"顺手补上"；
- `IconButton` **一律不写 `title`**：外面有 `Tooltip` 就不再叠一层，没有就自己补一个
  （靠 `Tooltip` 提供的 context 判断，见 `useInsideTooltip`）。于是同一排按钮的提示观感一致，
  也不会出现"鼠标一停冒出两个面板、还写着两句不同的话"；
- 面板位置量的是**子元素**的矩形，不是外层包裹的：外层只是个 `inline-flex` 壳，
  子元素若是 `position: absolute`（消息区右下角那对"回到最上 / 最新"），外层会缩成
  零尺寸停在容器左边缘 —— 拿它算位置，提示会飘到屏幕另一头。
  这种"包一层"引发的错位很隐蔽：布局看着完全正常，只有浮层跑掉了（用例里把它钉住了）；
- 按钮提示**写短**：它是"这个按钮干什么"，不是说明书。带括号的长解释（含 Ctrl+B、
  端点说明之类）要么挪去设置项自身，要么精简 —— 一屏排开十几个按钮时，
  两三行高的提示比没有提示更碍眼；
- **收起要盯的不只是 `mouseleave`**（用户反馈："有些浮动窗口在某些情况不会消失"）。四种情形
  `mouseleave` 都指望不上，各有对应做法：
  1. **按下去**（触发元素弹出了菜单/面板，指针还在原地）→ `pointerdown` 就收起；
  2. **焦点转移**（点了别的控件、菜单拿走了焦点，而窗口没有失焦）→ `focusin` 时若焦点
     不在触发元素内部就收起（判据必须是"在不在里面"，否则键盘 Tab 到按钮就看不成提示了）；
  3. **切到后台**（Alt+Tab）→ `blur` + `visibilitychange` 都挂（有的窗口管理器只发后者）；
  4. **元素被卸载**（行被过滤掉、面板被关闭）→ 元素的存亡**没有事件可听**，但"被移除"
     本身是一次 DOM 变动，所以用一个 `MutationObserver`（只在有面板挂着时存在）。
     这里**刻意不用 rAF 轮询**：没有渲染循环的环境（jsdom）里帧回调不保证触发，
     而这条规则正要靠用例钉住。
  **一个反直觉的坑**：走"包一层"那条路径时，`anchorRef` 指的是**我们自己的包裹 span** ——
  它不会随里面的子元素被替换而消失，所以只看它永远判不出"触发元素已经没了"
  （探针实测：换完子元素后包裹 span 依旧 `isConnected === true`）。因此额外记一份
  包裹内部的第一个元素，判断时**两层都要在**（见 `innerRef` 的注释）；
- **浮板只由两个"真实动作"点亮，其余一律不点**（这是"关掉面板后浮板还在"的根治办法）：

  | 路径 | 判据 |
  |---|---|
  | 指针（`mouseenter`） | 指针**真的动过**（`pointerDismissedRef` 未置位） |
  | 键盘（`focus`） | **刚按过移动焦点的键**（`navKeyRef`：Tab / 方向键） |

  **根因（三层叠出来的一个 bug，值得记下来）**：① 关闭面板时 `useModalFocus`
  会把焦点**还给当初打开它的那个按钮**；② 那一次 focus 被 `focus` 路径当成"用户在指向它"；
  ③ 而当时"按任意键就解除抑制"这条过宽的规则，让在面板里按 Tab / 按 Esc 就提前把防线撤了。
  于是"点开设置 → 关掉设置 → 浮板又冒出来"，**而那时指针根本不在按钮上** ——
  正是这一条把根因锁死在 focus 上（`placeAround` 只有 mouseenter / focus 两个调用点，
  指针不在元素上就排除了前者）。
  修法是**把判据收紧**而不是加代码：指针路径等一次真实 `pointermove`；
  键盘路径只认"移动焦点的键"，Esc 更相反 —— 它是"退下"，顺手把键盘路径也关掉。
  这套"点击 + 滚动就收起、并要求一次真实动作"的思路参考了作者另一个项目 ImgVaguer
  （那里是 document 级委托浮层，注释写得直白：**目标被移除 / 弹窗打开 /
  滚动时不会触发 mouseout，需在这些时机强制收起**）；
  `navKeyRef` 的维护必须是**常驻**监听：它要回答"这次 focus 是不是 Tab 来的"，
  而那一刻浮板还没显示 —— 放进显示期的监听里，键盘用户就永远看不到提示了
  （这条错误被用例当场抓到过）；
- **滚动（捕获阶段）也收起**：提示是按点击那一刻的坐标 `position: fixed` 定位的，
  滚动时不收会停在原地、与被指向的控件错位；用捕获阶段才听得到内层滚动容器；
- 不变量由 `tests/ui/tooltipSingle.test.tsx` 钉住：按钮身上永不带原生 `title`、
  悬停时最多一个 tooltip、面板跟随子元素位置。

## 几条容易改坏的交互细节

都不是"好不好看"的问题，而是不这样做用户就会以为程序坏了：

- **发送之后一定贴到底**（`MessageList`）：用户往上翻历史时自动跟随会松开（这是对的），
  但他接着打字并**发送**时，那条消息必须看得见 —— 点了发送却停在半空，看谁都像没发出去。
  判据是"激活路径的最后一条变成了用户消息"：这恰好等于"刚刚按下发送"，
  流式输出与翻看历史都不会误触发。别改成"内容一变高就贴底"——那用户就没法读历史了；
- **数字输入框的箭头是自绘的**（`primitives/Controls`）：原生那两个
  （`::-webkit-inner-spin-button`）不跟主题，还会与单位文字抢同一个位置
  （于是早先只好给输入框留 34px 内边距，而那个数是猜的）。现在是
  "整只控件一个框，框里 = 输入 + 单位 + 自绘箭头"，箭头悬停/聚焦才显形（一屏七八个
  数字框时不会发吵）。键盘的上/下键仍然原生可用，没有被拿掉；
- **删除按钮用危险色**（`MessageItem.module.css` 的 `.danger`）：那一排动作里只有它不可撤销
  （编辑能撤回、重新生成能换一版、复制无害）。选择器刻意写成 `.actions .danger`（两级）——
  `.iconButton` 的基色也是单类选择器，谁赢取决于两个 CSS Module 的插入顺序，
  而那种"靠 import 顺序生效"的样式迟早会在一次无关调整里失效；
- **「继续写」常显、且不进那排图标按钮**（`MessageItem` 的 `.continueRow`）：
  那排图标是悬停才显形的，而"现在该你决定了"藏进去就等于没做。它带强调色但**不填实色**——
  填实会与发送键争"最主要的那个按钮"，而这里问的是"要不要再来一轮"，不是"提交"；
- **两个"跳到这条消息的哪一头"的按钮分开放**（`MessageItem` 的 `.toTop` 与 `.actions` 第二行）：
  「跳转到消息顶部」挂在**气泡自己的侧边底部**（小圆钮，取操作条的**对侧** —— 助手靠左、用户靠右，
  两个可点区域不会挤在一起）；「跳转到消息底部」在操作条里**单独占一行**（那一排按钮的换行下方，
  所以操作条整体是纵排、图标仍在 `.actionRow` 里横排，宽度照旧固定 116px）。
  两者都跟操作条同一套显隐规则。滚动由 `MessageList.jumpToMessage` 做，
  它按 **rect 差值**算目标位置（`offsetTop` 相对的是最近的定位祖先，不一定是滚动容器），
  并且**必须回写 `pinnedTopRef`** —— 不写的话这次跳转会被 `onScroll` 当成"用户往上翻"，
  当场掐断自动跟随；跟随意图按**落点**重判，跳到顶部就停下读、跳完仍贴着底才继续跟。

## 搜索高亮

用 **CSS Custom Highlight API**（`ui/utils/searchHighlight.ts` + `styles/searchHighlight.css`），
而不是往 DOM 里插 `<mark>`：插节点会和 React 的 DOM 管理直接打架 —— React 记着自己渲染了哪些节点，
下一次重渲染去移除子节点时会抛 `NotFoundError`（流式输出期间每 120ms 就有一次重渲染，
这类错误只在特定时序出现，极难复现）。Highlight 高亮的是**文本区间**，DOM 一个节点都不动。

高亮的输入是"状态 → 画面"的一次映射（`SearchPaintInput`），并且挂了 `MutationObserver`
（rAF 合并同帧的多次变动）：DOM 一变就用同一份输入重画 —— 思考过程展开、流式替换正文、
切换变体都会让上一次的区间指向已不在文档里的文本节点，没有这个自愈就会出现
"高亮偶尔消失，再点一下又回来"。详见 [04-search.md](./04-search.md)。

## 通知与警报

`components/Notices.tsx` 是挂在 `App` 根部的通知条，聚合**六个来源**：
`chatStore.error`、`chatStore.persistenceError`、`workspaceStore.error`、`workspaceStore.alerts`
（例如"AI 想改文件但没拿到授权"）、`storageStore.status.error`、以及 **`uiStore.notices`** ——
通用的那一个：任何地方想告诉用户一句话，就 `pushNotice({ tone, message })`。
它存在的原因是**别再 `window.alert`**：alert 打断、不可测、样式不跟主题，
而"要告诉用户点什么"以前只有 alert 或塞进某个 store 的错误字段（后者等于看运气）。

通知还能带**一个动作**（`Notice.action`，目前只有"撤销"）：对"一击就覆盖用户手写内容"的操作
（恢复默认设置、清空余额脚本、删除模型配置、把本会话覆盖全部恢复为继承），这条通道比确认框合适 ——
正常操作一次点击就过，只有真做错了才需要那一下。**只给能如实复原的动作**：
复原不了的（已经发出去的请求、删掉的外部文件）不该有这个入口，那种情况弹确认才对。

两个"容易漏掉"的来源值得单独说，它们都来自同一个教训 ——**屏幕看着正常，其实有事**：

- `persistenceError`（`ChatService` → 快照）：内容**没能写进本地库**。命令失败用户马上能看见，
  而这个不会：回答一个字不少地长出来、能复制能编辑，只有重开页面才发现它没了。
  写入恢复后它自己清掉（是当前状态，不是历史）；
- `storageStore.status.error`：本地存储本身有问题（库读不出来、被重建、写入失败）。
  它以前**只出现在「设置 → 关于」**里 —— 而装载失败的用户看到的是一个空白界面，
  他不会想到去设置页找原因，只会以为"本来就没数据"。地基出问题必须在他眼前说清楚。

- **为什么不塞进某个面板**：这类事件**没有归属的组件** —— 用户可能压根没打开工作区设置。
  塞进任何面板都会变成"只有碰巧打开那个面板的人才知道发生了什么"；
- **它只管人**：模型那边收到的是工具失败返回的 `FS_EDIT_DENIED`（由工具循环转成一条
  失败的 `tool_result`）。那是另一条通道，不要想着用通知条去"告诉模型"；
- 层级用 `--z-toast`：通知是临时性的，面板开着时也该看得见；
- 容器带 `aria-live="polite"`，屏幕阅读器会念出来。

## 面板拆分（设置面板）

`SettingsPanel.tsx` 只剩**编排**：状态、键盘、导航、按 `section` 分发（约 170 行）。
9 个分区在 `panels/settings/*.tsx`，各自决定要不要 props：

- 只读一份全局状态的分区（外观 / 关于 / 输入与快捷键）自己调 store / `useTheme()`，不接 props；
  **没有「工作区」分区**：它是每个会话各自选的目录，不是全局默认值 —— 入口只在会话设置与顶栏；
- 跨分区的界面状态（如续写档位 `modeTab`）留在外壳，作为 props 传下去 —— 单一来源；
- 分区之间**共用**的样式放 `panels/settings/sections.module.css`：`check:styles` 是**按文件**
  算"定义了没人用"的，类留在外壳的 module 里会被拆出去的分区用不到而被报成死样式。

## 模态面板的焦点

三个覆盖层面板（设置 / 本会话设置 / 角色）都声明了 `aria-modal="true"`，
所以它们**必须**管好焦点：`useModalFocus` 负责三件事 —— 打开时把焦点移进面板、
`Tab` / `Shift+Tab` 在面板内循环、关闭时把焦点还给打开它的那个元素。

只在这三件事上接管，中间的 Tab 不拦：完全接管会让浏览器默认行为
（含 `:focus-visible` 的判定与读屏播报）失效。

> 这类"焦点在哪儿"的行为**是可以在 jsdom 里测的**（`tests/ui/modalFocus.test.tsx`），
> 不要因为"UI 测不了"就放过它 —— 测不了的是布局，不是交互。

### 点遮罩关闭：按下与松手都要在遮罩上

**不能只写 `onClick={close}`**：`click` 会被派发到 mousedown 与 mouseup 的**共同祖先**上，
于是"在面板里按住、拖到外面松手"这一次手势，click 的目标变成了遮罩 → 面板被关掉
（用户报的：按住不放、移到面板外松手，面板关了；他不是想关它）。
`useOverlayDismiss` 把两次都记下来，只有**两次都落在遮罩本身**才算点遮罩
（面板里也不用再写 `stopPropagation`：它只能挡"从面板内部发起"的 click，
挡不住拖出去的那一次）。用例：`tests/ui/overlayDismiss.test.tsx`。

## 文案：一行说清，不写解释性括号

面向用户的每一句（`help` / `Tooltip` / 状态文字）都遵守同一条：

- **说"做什么 / 会怎样"，不解释实现** —— 用户不需要知道它内部怎么算的；
- **不写解释性括号**（"已授权（不会被系统自动清理）"这种）。括号里的信息若真有用，
  就写成实词："已授权" / "数据仍会保存，但磁盘紧张时可能被回收"；
- 长度上**一行能读完**为准。这条被反复提过两次，所以写进文档当约定，
  改文案时照着来（`Tooltip` 是 `?` 图标旁边那一段，用户点开就是为了省时间，
  看到"小作文"比不写更糟）。

## 加东西时的落点

| 加什么 | 动哪几处 |
|---|---|
| 一个面板 | `ui/panels/X.tsx` + `X.module.css`，`App.tsx` 里 `lazy()` 挂上，`uiStore` 加一个 `PanelId`，`check:styles` 会自动盯 `styles.x` 是否有定义 |
| 一个设置项 | `domain/value-objects/appSettings.ts`（字段 + 默认值）→ `ui/panels/settings/XSection.tsx`（控件） |
| 一个可拖动列表 | 用 `useDragReorder` + `DragHandle`，别自己写一套 |
| 一个覆盖层（菜单/气泡） | `position: fixed` + portal 到 `body`，层级用 `--z-dropdown` / `--z-modal`，别用绝对定位挂在裁剪容器里 |
